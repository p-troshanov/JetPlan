# Критические security controls

Документ фиксирует реализованные границы безопасности для Docker-сборки, категорий задач и привязки Telegram.

## Docker build context

- backend image копирует только `backend/` и `requirements.txt`;
- корневой и frontend `.dockerignore` исключают `.env*`, локальные зависимости, сборки и IDE-артефакты;
- runtime-секреты должны передаваться через environment и не должны находиться в слоях нового image.

Изменение не удаляет уже созданные image layers. После поставки нужно пересобрать server images и определить, публиковались ли старые образы за пределы доверенного сервера. При подтверждённой публикации секреты требуется ротировать.

## Владение категориями задач

`POST /api/tasks` и `PUT /api/tasks/{task_id}` принимают `category_id` только если категория принадлежит аутентифицированному пользователю. `null` остаётся допустимым значением для задачи без категории. Тот же allowlist применяется к category id, возвращаемым AI в Telegram-контуре.

Чужой или несуществующий `category_id` отклоняется до записи задачи с HTTP 400 без раскрытия данных категории.

## Привязка Telegram

Код привязки является высокоэнтропийным одноразовым challenge. HMAC-подпись связывает его с id текущего web-пользователя и `SECRET_KEY`, поэтому challenge другого пользователя не проходит проверку даже при раскрытии значения.

- срок действия остаётся 10 минут;
- старые четырёхзначные коды намеренно больше не принимаются;
- новый код нужно копировать из сообщения Telegram целиком;
- Telegram, уже занятый другим web-аккаунтом, возвращает HTTP 409 вместо ошибки уникального ограничения БД;
- общая защита auth endpoints от частых запросов остаётся отдельной задачей в `backlog.md`.

## Проверка

Критические инварианты покрыты стандартными `unittest`-тестами:

```powershell
venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тесты проверяют Docker ignore policy, user binding и tamper detection Telegram challenge, отказ от legacy-кодов и обязательный owner filter категории.
